1. What the “undercut” actually is

In removable partial denture (RPD) design, an undercut is a region of a tooth/arch that lies below the survey line relative to the chosen insertion direction — the part that would mechanically block a rigid appliance from seating. The backend surveys the jaw and produces an undercut heatmap: a colour per mesh vertex, ramping yellow → orange → red as the undercut depth grows (0.25 → 0.5 → 0.75 → >0.75 mm).

The backend ships that heatmap as surveying_values — a packed Float32Array of RGBA per vertex. The colour for vertex i sits at heatmap[i*4 … i*4+3], and the sentinel (1,1,1) means “no undercut here, keep the base tooth colour.”

surveying_values (Float32, 4 floats per vertex) vertex 0 vertex 1 vertex 2 ... ┌───┬───┬───┬──┐┌───┬───┬───┬──┐┌───┬───┬───┬──┐ │ R │ G │ B │ A││ R │ G │ B │ A││ R │ G │ B │ A│ └───┴───┴───┴──┘└───┴───┴───┴──┘└───┴───┴───┴──┘ ▲ └─ colour of mesh-vertex 0 → so mesh-vertex i MUST equal heatmap-vertex i
The core requirement For the heatmap to paint correctly, the rendered mesh’s vertices must be in the exact same order and count as the array the backend surveyed. Colouring is a simple copy — if the indices line up.

2. The root cause — it was never a colouring bug, it was a topology mismatch

The jaws were fetched as STL. STL is a “triangle soup” format: it stores three raw vertices for every triangle, with no vertex sharing. A single physical corner shared by, say, six triangles is written out six separate times. So a raw STL mesh has many more vertices — in a completely different order — than the indexed, deduplicated mesh the backend computed the heatmap against.

INDEXED mesh (what the backend surveyed) STL "triangle soup" (what the browser loaded) v2 corner P appears 6× as distinct verts: /\ tri A → P, … (vertex 11) / \ 4 shared vertices tri B → P, … (vertex 27) v0────v1 2 triangles tri C → P, … (vertex 40) \ / = heatmap has 4 entries … … \/ same point, 6 indices → counts & order differ v3 → heatmap[i] lands on the WRONG point

Map heatmap entry i onto STL vertex i and the colours smear across the surface, because index i in the soup is not the same physical point as index i in the backend’s indexed mesh. That is the undercut bug.

3. The earlier approach that didn’t fully work (commit ece1767)

The first attempt tried to reverse-engineer the backend’s deduplication from the STL soup so the vertex counts (and hopefully order) would match. Three functions carried it:

  • estimateBackendThreshold() — binary-searches a vertex-merge distance until the deduplicated count matches the heatmap’s vertex count.
  • buildDualDedupGeometry() — dedups the soup twice (our threshold + the estimated backend threshold) and builds a surrogate mapping from each of our vertices to the backend vertex it first co-occurs with in the raw stream.
  • smoothVertexColors() — Laplacian-smooths the result several times to wash out the speckle from the inevitable misalignment.
// buildDualDedupGeometry — the heuristic: guess the backend's merge threshold,
// then hope each vertex co-occurs with the right backend index in the raw stream.
const backendThreshold = estimateBackendThreshold(positions, targetBackendCount);
...
// colours come from spatial co-occurrence, not a guaranteed 1:1 alignment
if (ourVertToBackendIdx[ourIdx] === -1) ourVertToBackendIdx[ourIdx] = backendIdx;
...
smoothVertexColors(geometry, 5); // 5× blur to hide the misaligned-vertex streaks
Why it stayed wrong Matching a vertex count does not guarantee matching a vertex order. The mapping was a statistical guess, so colours landed approximately — then 5× Laplacian smoothing blurred the errors into soft blobs. The code’s own comment concedes it: “Without backend positions we can’t get exact per-vert alignment with the heatmap, so the raw colours are noisy… heavy smoothing collapses the misaligned-vert streaks.” Result: a fuzzy approximation, not the crisp desktop render.

4. The fix — change the data, not the math (commits fb792d8 → dd3d3ab)

Instead of fighting STL’s lost vertex-sharing, the fix switches the transport format to OFF. OFF (Object File Format) is an indexed mesh: it lists each unique vertex once, then lists faces as indices into that vertex list — the same representation the backend used to compute the heatmap.

OFF payload ┌──────────────────────────────┐ │ OFF │ │ 4 2 0 ← 4 verts, 2 faces │ x0 y0 z0 ← vertex 0 ────┼──► heatmap[0] 1:1, no guessing │ x1 y1 z1 ← vertex 1 ────┼──► heatmap[1] │ x2 y2 z2 ← vertex 2 ────┼──► heatmap[2] │ x3 y3 z3 ← vertex 3 ────┼──► heatmap[3] │ 3 0 1 2 ← face (indices into the vertex list) │ 3 0 2 3 │ └──────────────────────────────┘

Because vertex i in the OFF file is heatmap vertex i, colouring collapses to a direct copy with none of the dedup/threshold/smoothing machinery.

4.1 — Sniff the payload format: inspectMeshPayload()

Reads the first bytes of the decoded buffer and classifies it, so the renderer knows whether it received OFF, ASCII STL, binary STL, or junk.

function inspectMeshPayload(buffer) {
  // build a printable preview of the header bytes
  if (upperHeader.startsWith("OFF"))      return { format: "off", ... };
  if (/^SOLID\b/i.test(trimmedHeader)) return { format: "ascii-stl", ... };
  if (byteLength >= 84) {                 // binary STL: 80-byte header + uint32 tri count
    const triangleCount = view.getUint32(80, true);
    const expected = 84 + triangleCount * 50;
    return { format: expected === byteLength ? "binary-stl" : "unknown-binary", ... };
  }
  return { format: "unknown", ... };
}

4.2 — Keep only renderable files & prefer the right source: filterRenderableJawFiles()

Each fetched file is tagged with __payloadInfo / __sourcePath and dropped if it isn’t a real mesh. fetchJawFilesForCase() now selects /stl/get only if it yields a renderable mesh; otherwise it falls back to /stl/raw/get, then the per-jaw route.

const all = await tryEndpoint(`${BASE}/stl/get`, payload);
const validAll = filterRenderableJawFiles(all, "/stl/get");

4.4 — Why the colour function is now trivial: applyUndercutVertexColors()

// vertex i  ←  heatmap[i*4]   — no dedup, no threshold search, no smoothing
for (let i = 0; i < limit; i += 1) {
  let r = heatmap[i * 4], g = heatmap[i * 4 + 1], b = heatmap[i * 4 + 2];
  if (r === 1) r = DEFAULT_TOOTH_COLOR[0];   // (1,1,1) = "no undercut" sentinel
  if (g === 1) g = DEFAULT_TOOTH_COLOR[1];
  if (b === 1) b = DEFAULT_TOOTH_COLOR[2];
  colors[i*3] = r; colors[i*3+1] = g; colors[i*3+2] = b;
}
Why it works now OFF arrives already indexed in the backend’s own vertex order, so mesh-vertex i === heatmap-vertex i is guaranteed by the format — not approximated. The colour application is a one-to-one copy, which is why the render is crisp and matches the desktop app, with zero threshold estimation, surrogate index mapping, or Laplacian blurring.

6. One-sentence summary

TL;DR The undercut was a mesh-topology mismatch: STL throws away vertex sharing while the heatmap is per-shared-vertex, so the old code tried to statistically rebuild the backend’s vertex set and blur over the errors. The fix sidesteps it by requesting an OFF (indexed) mesh whose vertex order already matches the heatmap, turning the colouring into a direct copy.
